The early-commitment problem

Streaming speech translation must emit target words before hearing the full source.

What is simultaneous translation?

Speech is streaming in — Chinese subtitles must appear with low latency, while English is still being spoken. The system must emit target tokens before seeing the full source.

Core issue: once a Chinese character is emitted, it's frozen. If later English reveals we were wrong, we can't take it back.

Example — when wait-k goes wrong

EN observed (wait-k=3): "The bank was..."
→ naïve early commit: "银行..." ❌ (commits to financial bank)
→ EN continues: "...teeming with frogs and dragonflies"
→ correct ZH: "河岸上青蛙和蜻蜓蜂拥" ✓ (bank = riverbank)

Research question: can we replace rigid wait-k with a content-adaptive commit rule — emit a Chinese token only when it's safe under all plausible English continuations?

Key move: by shifting from character-level string matching to token-level distribution consensus, Token Consensus preserves LCP's safe-prefix intuition while tolerating the lexical diversity of Chinese translation.

Token Consensus Decoding — one commit step

Qwen3-30B-Instruct (translator, vLLM) + Qwen3-4B-Base (English future LM).

1
Sample K=10 English futures from the observed source prefix using Qwen3-4B-Base
↓
2
For each future fi, query Qwen3-30B-Instruct (via vLLM /completions) for next-token top-10 distribution, using apply_chat_template + assistant-prefix forcing so the model continues from the committed Chinese prefix
↓
3
Filter each distribution — remove special tokens, English-letter tokens, garbled/control characters
↓
4
Hard intersection of the K top-k token-ID sets ⇒ set of tokens agreed by all futures
↓
5
If non-empty: pick the token with the highest average probability across futures → APPEND. Loop
↓
6
If empty: READ more source, retry at next policy call
↓
7
Trim pending tokens to a clean UTF-8 boundary before committing
Every committed Chinese token/span is one on which all 10 plausible English continuations agree in the translator's next-token distribution — this is what makes the commit safe.

What worked, what didn't, what's sensitive

Key findings across the three methods.

✅ What worked

  • Token-level consensus beats character-level LCP — solves lexical-variation problem on Chinese names
  • Prefix-forcing via apply_chat_template + assistant-prefix is the key enabler
  • Hard intersection with top-10 logprobs is a practical sweet spot
  • Same progression on both text (WMT19) and cascaded speech (CoVoST)

❌ What didn't work

  • Beam refinement (legacy EN→DE probe): +0.2 BLEU for 4× compute — ruled out
  • Entropy-only gating: too blunt — signal says "risky" but offers no answer
  • Continuation-style decode: no improvement; abandoned early
  • SemLCP without chat-template: −2.3 BLEU — prompt formatting is critical

⚠️ What's sensitive

  • TC compute cost: K=10 concurrent next-token queries per commit step — latency hides it, but GPU-compute scales linearly in K
  • TC top-k: too permissive (top-20) lets noise in; too strict (top-5) triggers empty-intersection more often
  • Hard intersection is conservative at K ≫ 10 — soft quorum may help

Contributions & next steps

One algorithmic idea, validated across speech and text.

🎯 Contributions

  1. Progressive decomposition of early commitment — "when to wait" (DD) → "what chars are safe" (LCP) → "what next token is safe" (TC). Each step addresses a concrete limitation of the previous.
  2. Token Consensus Decoding — a novel commit rule that intersects token-level distributions across K sampled English futures, robust to Chinese's lexical surface variation.
  3. Validation on the real speech task — same progression holds on CoVoST-2 cascaded ST and WMT19 text, and transfers to NLLB-600M translators.

🔮 Next steps

  • End-to-end speech model — skip the cascaded ASR front-end
  • Soft quorum consensus — replace hard intersection with ≥ q % agreement to improve recall at larger K
  • Transfer to other language pairs — EN→DE, ZH→EN, especially languages with richer morphology
  • Joint compute-latency optimization — adapt K per commit step based on source difficulty
